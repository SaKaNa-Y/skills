# Finding identities before repair groups

Date: 2026-10-31. Applied to source only.

A repair assessment can follow old record boundaries and stop after finding one more affected caller. Assess now traces the failing operation outward to public entry points, then checks the inputs and prior state each path accepts. A default construction path does not exclude another supported path. The batch procedure reaches this check before it groups fixes.

Identity decisions now distinguish one failure across several entry points from independently violated conditions within a shared contract. Separate edits do not prove separate problems. A combined correction alone does not prove duplicate observations. The assessment checks what a comparison changes, preserves individual failure conditions and acceptance, and decides delivery groups after it updates the problem scopes.

Six fresh agent runs used ordinary assessment requests with no relationship reminder or supplied diagnosis. In a real-project snapshot, the baseline and first candidate both found another caller but missed an accepted-state branch. The revised candidate found and exercised that branch, then updated the existing record. In a small independent-domain fixture, the first candidate claimed duplication from a comparison that changed two conditions. The revised candidate used separate interventions and retained the independent failures and masking relationship. The baseline also handled that fixture correctly. Review corrected an overly rigid expected identity count; evidence and retained acceptance determined the result, not a required PR count.

These runs support the revised method in the examined cases. They do not establish general reliability or a statistical improvement. The second fixture became development evidence after revision. All actors used the same recorded model and effort, but shared-host filesystem isolation relied on task boundaries. No product repair or external publication was performed by the trials.
