# Keep Personal Preferences Outside Shared Skill Methods

Skill evolution may learn from an individual's use, but a personal preference alone does not justify changing the shared skill. Promote methods that serve the target's intended domain beyond that user's identity; keep preferences about that user's presentation or workflow in the usage context. Generality means serving the skill's intended range of use, not expanding it into unrelated responsibilities.

Automatically turning preferences into optional modes would grow the skill's interface and maintenance burden. Maintaining personal forks would create a separate version relationship to manage. Neither is the default evolution outcome. A variation later supported as a recurring domain need can receive a separate discussion about whether an optional capability is warranted.

A single clear observation can still motivate a hypothesis. Before adoption, state its domain-level benefit and applicability conditions, then challenge it with relevant variations in user needs and boundaries where the method should remain inactive. Validation supports the observed scope; abstract wording alone does not establish generality.

Each iteration also examines the resulting method as a whole against the skill's purpose and explicitly agreed responsibility boundaries. This exposes accumulated narrowing, personal defaults, duplication, conflicting rules, and unnecessary branching that a review of the latest diff alone could miss. Behavioral probes remain proportional to the current change; a whole-method review does not require replaying every historical scenario or authorize unrelated rewrites.
