# Issue drafting and revision

Date: 2026-10-31. Source added. Installation unchanged.

A detailed engineering discussion and an issue draft serve different purposes. Copying every design decision into a proposal can obscure the request. Later wording revisions can also leave a saved draft behind the conversation.

`issue-writing` helps the user clarify an idea, shape a draft for its audience, and revise the latest version. It preserves essential conditions and the author's uncertainty. An agreed local draft is synchronized when the complete current version is delivered. Discussion and small edits can finish without producing a full issue.

The skill requires explicit invocation. It allows bounded relevant read-only checks. The user submits the draft. Tracker writes, publication prompts, automatic engineering logs, and automatic commits are outside this workflow. Existing assessment, discovery, and triage skills retain their responsibilities.

Instruction review found and corrected two scope conflicts before adoption. A fresh five-turn exercise covered clarification, drafting under a fixture template, two unselected alternatives, a selected paragraph revision, and final delivery. Direct file comparisons confirmed that alternatives left the saved draft unchanged, the selected revision preserved other paragraphs, and the detailed decisions stayed unchanged. Separate continuation exercises covered a defect report with missing evidence and an implementation request with unrun tests.

These bounded cases support the tested method, not a general improvement over other skills. The exercise coordinator supplied sequential user turns and checked file contents. Full child tool-event logs were not retained, so remote non-mutation rests on instruction review and observed responses rather than a complete tool audit. Recovery snapshots are kept locally under the repository history policy. The installed copy remains unchanged.
